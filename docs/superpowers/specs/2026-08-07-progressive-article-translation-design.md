# 渐进式全文翻译设计

## 目标

长文章执行全文翻译时，应尽快展示已经完成的译文，而不是等待全部批次完成。翻译结果必须逐批持久化，刷新页面后能够从已完成位置继续；单批失败不得清除其他成功结果。

## 当前问题

当前全文翻译把自然段按约 6000 字符组成批次，在一次 HTTP 请求内串行调用模型。每次模型调用最多等待 30 秒，所有批次全部成功后才统一保存并返回。因此长文的总等待时间会累加，任意批次失败也会使本次已完成结果无法使用。

## 批次规则

- 第一批优先翻译标题和文章开头，正文目标上限为 500 个 Unicode 码点；如果首个自然段本身超过 500 个码点，则该段独占第一批。
- 后续批次以自然段为边界，每批目标范围为 800–1200 个 Unicode 码点。
- 不拆分自然段。单个自然段超过 1200 个码点时，该段独占一个批次。
- 批次划分必须由服务端根据当前文章内容确定，客户端只引用批次序号。
- 批次划分算法由翻译规则版本标识；规则版本变化时不复用旧结果。

## 存储模型

新增按自然段保存的全文译文表。每条记录至少包含：

- `article_id`
- `user_id`
- `source_hash`
- `rules_version`
- `paragraph_index`
- `translation_zh`
- `model`
- `updated_at`

主键或唯一约束覆盖用户、文章、原文哈希、规则版本和段落序号，使两个并发批次可以独立 upsert，不会发生 JSON 整体覆盖。标题译文保存在文章翻译元数据记录中，并与相同的原文哈希和规则版本绑定。

旧的完整 `article_translations` 结果继续可读。新流程全部完成后可返回与现有前端兼容的 `status: "fresh"` 完整结果；处理中返回 `status: "partial"`。

## API

### 查询状态

`GET /api/articles/:articleId/translation`

返回当前文章对应的翻译状态：

- `status`: `missing`、`partial` 或 `fresh`
- `sourceHash`
- `rulesVersion`
- `titleZh`（如已完成）
- `paragraphs`: 已完成的段落译文
- `batches`: 每批的序号、段落索引和完成状态
- `completedBatches`
- `totalBatches`

接口只返回当前文章哈希及当前规则版本对应的结果，不展示过期译文。

### 翻译单批

`PUT /api/articles/:articleId/translation/batches/:batchIndex`

请求体包含客户端查询状态时得到的 `sourceHash` 和 `rulesVersion`。服务端重新读取文章并验证二者，再按确定性规则获得对应批次。客户端不得提交待翻译正文。

成功响应包含本批已保存的标题译文（如有）、段落译文及最新进度。重复请求同一个已完成批次时直接返回已保存结果，避免重复调用模型。

如果文章已修改，返回 `409 TRANSLATION_SOURCE_CHANGED`；如果规则版本不匹配，返回 `409 TRANSLATION_RULES_CHANGED`，客户端随后重新查询状态。

## 前端调度与展示

点击“翻译全文”后立即切换到全文翻译视图，不等待整篇完成：

1. 查询当前状态并立即渲染已有译文。
2. 未完成段落保留原文位置，并显示轻量等待状态。
3. 如果第一批未完成，单独优先请求第一批。
4. 第一批完成并显示后，最多同时运行两个后续批次。
5. 每批成功后立即合并响应、更新对应段落和进度文案，例如“已翻译 4/12 批”。
6. 页面刷新或重新进入时只调度缺失批次。
7. 切换回原文时不再启动新批次；已经发出的请求允许完成并持久化。

同一页面只维护一个全文翻译调度器。刷新全文翻译会使当前调度代次失效，重新读取服务器状态后继续，旧响应不得覆盖新状态。

## 上下文与质量

每批模型请求包含文章标题、本批自然段、固定翻译规则，以及必要的相邻原文上下文。只要求模型返回本批段落的译文。固定温度、模型、规则版本和结构化输出要求，以降低并行批次之间的风格差异。

第一批使用较小输入以缩短首次可见时间；后续批次适度增大以减少请求数量。上线后记录每批输入长度、模型耗时、成功状态和重试次数，再根据真实 P50/P95 调整 500 与 800–1200 的范围。

## 失败与恢复

- 单批超时、模型暂时不可用或格式校验失败时自动重试一次；文章冲突、规则冲突、输入错误和额度限制不自动重试。
- 第二次失败后停止自动重试该批，保留其他成功译文，并提供“继续翻译”入口。
- 遇到额度限制时停止启动所有后续批次，保留已完成内容并显示明确提示。
- 格式校验失败仅影响当前批次，不写入不完整数据。
- 并发请求乱序完成时按段落索引合并，不按响应顺序排列。
- 文章修改后旧哈希结果不再展示；正在运行的旧请求在保存前再次验证文章内容。
- 关闭或刷新页面不保证未完成请求继续运行，但已保存批次可在下次进入时恢复。

## 测试

服务端测试覆盖：

- 第一批正文目标上限为 500 个码点并包含标题翻译任务；首个自然段超长时验证其独占第一批。
- 后续批次以自然段划分，目标为 800–1200 个码点，超长自然段独占一批。
- 单批成功即持久化，并发 upsert 不互相覆盖。
- 已完成批次重复请求不再次调用模型。
- 部分状态和完整状态响应正确。
- 原文变化、规则版本变化、格式错误、超时和额度限制均返回稳定错误。
- 保存前再次检测文章变化。

前端测试覆盖：

- 点击后立即进入全文翻译视图并显示已有部分结果。
- 第一批优先；完成前不启动后续批次。
- 后续并发数始终不超过 2。
- 每批完成后立即渲染并更新进度。
- 乱序响应按段落索引显示。
- 刷新后只恢复缺失批次。
- 离开全文模式后不启动新批次，旧响应仍可安全落库但不错误改变当前界面。
- 自动重试仅执行一次，额度错误停止调度，手动继续可恢复。

## 不在本次范围内

- 不引入 Queue、Workflow、Durable Object 或常驻后台任务。
- 不实现逐 token 的流式译文展示。
- 不在自然段内部拆分超长段落。
- 不更换现有翻译模型。
